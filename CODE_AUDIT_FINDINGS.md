### 1. Inline edits (toggle Active / roster limit / staff target) silently wipe an activity's required certifications

- **Severity:** critical  ·  **Category:** bug  ·  **Subsystem:** Menu builder
- **Location:** `src/app/admin/menu-builder/menu-builder-client.tsx:387 / src/app/admin/menu-builder/actions.ts:113-117`
- **Status:** [ ] open

**What's wrong:** OfferingRow.inlineSave() builds a FormData for updateOffering that never includes any `certificationIds` entries (it only sets id, limitType, staffTarget, rosterLimit, and the boolean flags). updateOffering() unconditionally rewrites the activity's certifications inside the transaction: it calls activeCertificationIds(formData.getAll('certificationIds')) which returns [] when none are submitted, then runs prisma.activity.update({ data: { requiredCertifications: { set: [] } } }). Result: every inline action a user takes on a row — flipping Active, editing the roster limit, or editing the staff target — wipes ALL required certifications from that activity (and because the activity is shared across periods, from every offering of that activity). This is silent data loss triggered by ordinary, frequent UI actions.

**Suggested fix:** In updateOffering, only touch requiredCertifications when the form actually carried certification data (e.g. gate on `formData.has('certificationIds')` or a hidden marker emitted by the full edit modal). Do not derive 'clear all' from an absent field. Alternatively, have inlineSave re-submit the existing certification ids as hidden inputs.

<details><summary>Verification</summary>

Confirmed by reading both cited files. In menu-builder-client.tsx, OfferingRow.inlineSave (lines 387-413) constructs a fresh FormData and sets only id, limitType, staffTarget, rosterLimit, active, and the boolean flags (preAssigned, spansTwoPeriods, visibleOnMenu, visibleOnMasterMenu, includeInPrint, allowOverride, staffOnlyForCamperRegistration, notes). Because requiredCertifications is a relation on the shared activity (offering.activityId), the wipe propagates to every offering of that activity across all periods. The triggering actions (toggle Active, edit roster limit, edit staff target) are ordinary, frequent inline UI operations, so this is silent, easily-triggered data loss. Severity critical is appropriate.

### 2. Unknown CSV columns silently become bogus camper session designations

- **Severity:** high  ·  **Category:** bug  ·  **Subsystem:** Imports & data center
- **Location:** `app_files/src/lib/real-data-import.ts:312-316`
- **Status:** [ ] open

**What's wrong:** camperSessionDesignations() treats EVERY column not in knownCamperColumns as a checkbox-style session flag: `Object.entries(row).filter(([key, value]) => !knownCamperColumns.has(key) && isChecked(value))`. isChecked() (lines 319-322) returns true for any non-empty value that isn't in the blocklist ['0','false','no','n','unchecked']. knownCamperColumns only contains ~10 names (firstName, lastName, gender, genderIdentity, personAgeToday, campGrade, enrolledChildSessions, and the bunk columns). Real CampMinder/Webpoint exports contain many other columns (email, phone, address, parentName, dob, allergies, etc.). Each such column with any real value (e.g. an email address) passes isChecked()==true and is turned into a session-designation label via labelFromNormalizedKey(). The result: every imported camper gets spurious designations like 'Email', 'Phone', 'Parent Name'. Because importRealCampers (line 172) deletes designations with source:'import' and re-creates these on every import, the bogus labels persist and pollute the camper pool filters (sessionDesignations) used by rosters/registration/cards. This is the documented input format ('Use this as the admin entry point for CampMinder/Webpoint exports'), so it will fire on real data.

**Suggested fix:** Invert the logic: only treat a column as a designation if it is a known session-designation column. Drive checkedColumns from the keys of childSessionColumnLabels (an allow-list) instead of 'everything not in knownCamperColumns'. e.g. `Object.keys(childSessionColumnLabels).filter((key) => isChecked(row[key])).map((key) => childSessionColumnLabels[key])`.

### 3. Camper/staff import runs unbounded N+1 queries with no enclosing transaction

- **Severity:** high  ·  **Category:** perf  ·  **Subsystem:** Imports & data center
- **Location:** `app_files/src/lib/real-data-import.ts:127-185`
- **Status:** [ ] open

**What's wrong:** importRealCampers loops over every CSV row and, per row, issues sequential awaited queries: camper.findFirst (141), upsertCabin for the primary cabin (139), camper.create/update (159-161), then a nested loop calling upsertCabin + camperWeekEnrollment.upsert for each of up to 4 week blocks (163-170), then camperSessionDesignation.deleteMany plus a per-label upsert (172-179). For N campers this is on the order of N*(8-12) sequential round-trips with zero batching. importRealStaff (195-242) has the same shape. Critically none of this is wrapped in prisma.$transaction (contrast applyQ1Diff at actions.ts:363 which does), so a failure partway through a multi-hundred-row CampMinder export leaves the database in a half-imported state — some campers updated, their cabins upserted, others untouched — with no rollback. The route handler (api/import/campers/route.ts:19) just awaits the whole thing, so a timeout or single bad row aborts mid-way.

**Suggested fix:** Wrap the per-row writes in prisma.$transaction (or chunk into batched transactions) so a failure rolls back. Hoist cabin upserts out of the per-row loops by pre-resolving the distinct cabin names once into a Map, and prefetch existing campers/staff in a single findMany keyed by name instead of per-row findFirst.
